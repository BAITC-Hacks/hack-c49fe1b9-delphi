Дата: 23 сентября 2026 года.

В отдельной lab завершено согласование стадий/промптов, структуры, поиска исходного Before/After, перевода и resume; offline-проверка — 93 теста (92 успешных, один пропуск). ## 1. Короткий вывод

**Delphi хорошо спроектирован и имеет сильную backend-основу, но пока не готов к защите.**

Сейчас проект находится между этапами «код подготовлен» и «работающий продукт подтверждён». Backend уже содержит API, модели PostgreSQL, миграции, парсеры DOCX/Markdown/PDF/XLSX, агента с ограниченными инструментами, проверку доказательств, отчёты и OpenAPI-контракт. Однако frontend отсутствует, полный запуск с PostgreSQL и реальным AI ещё не подтверждён, а пользовательский путь от загрузки до отчёта не проверен.

Главная задача команды теперь — **не добавлять новую архитектуру**, а доказать один полный сценарий:

```text
Загрузить «До» и «После» → запустить анализ → открыть доказательства →
проверить вывод → скачать отчёт.
```

| Область | Состояние | Комментарий |
|---|---|---|
| Продуктовая идея и требования кейса | Хорошо определены | В фокусе перенос обязанностей, а не простой текстовый diff |
| Backend-код | Подготовлен | Модульный FastAPI, PostgreSQL, агент, парсеры, API, отчёты |
| Реальный API + PostgreSQL | Не подтверждён | Миграции, запуск контейнера и HTTP-сценарий нужно выполнить |
| Анализ с реальной моделью | Не подтверждён | Mock-тесты не доказывают качество на редакциях 8/9 |
| Frontend | Отсутствует | Это главный недостающий слой для жюри |
| Полный сценарий и demo | Не подтверждены | Нужны ручная приёмка, скриншоты и короткая запись |
| Авторизация | Не реализована сознательно | Не обязательна для MVP кейса; seed-пользователи — только задел на будущее |

## 2. Что уже сделано хорошо

### 2.1. Продукт не сводится к «чату с документами»

Это правильное решение. Кейсу нужен ответ на вопрос «кто теперь отвечает за функцию?», поэтому модель данных хранит подразделения, функции, исполнителей, область действия, условие и модальность. Такой подход сильнее обычного показа удалённых слов.

### 2.2. Доказательства защищены от выдуманных цитат

У каждого вывода предусмотрена связь `FindingEvidence → SourceBlock`. Модель возвращает идентификаторы, а сервер получает цитату из сохранённого оригинала. Это соответствует ключевому ограничению кейса: значимый вывод должен быть проверяемым по документу.

### 2.3. Хорошо разделены обязанности компонентов

```text
API → services → domain / models / parsers / agent / reporting
```

Маршруты тонкие, сервисы владеют транзакциями, агент ограничен инструментами чтения, а внешние DTO не совпадают напрямую с ORM-моделями. Это удобная структура для быстрого frontend и дальнейшего тестирования.

### 2.4. Учтены реальные риски документов

Парсеры и тесты уже учитывают сложные особенности предоставленных материалов: несколько пунктов внутри одного Word-абзаца, оглавление, пустой пункт, родительский контекст, нумерацию, нераспознанный скан и отсутствие приложения. Это заметно повышает доверие к демо.

### 2.5. У агента есть полезные ограничения

Один агент с `search_clauses`, `get_clause`, `get_unit_functions` и проверкой ссылок лучше нескольких «персон», которые трудно проверить. Перед выводом о потенциальной потере функция должна искать кандидатов по всему комплекту «После».

### 2.6. API готовится для нормального frontend-контракта

Стабильные `operationId`, Pydantic-схемы и `scripts/export_openapi.py` позволяют сгенерировать клиент через HeyAPI. Не нужно вручную копировать типы запросов между Python и TypeScript.

## 3. Важные несоответствия и риски

### P0 — нужно исправить или честно обозначить до демонстрации

1. **Root README устарел.** В [README.md](../../README.md) всё ещё сказано, что в репозитории только документация и исходные материалы, хотя в `backend/` уже есть значимый код. После того как backend будет добавлен в Git, README должен честно перечислить реализованные части и команды проверки. Не заявлять готовый продукт до полного запуска.
2. **Нельзя считать mock-тесты доказательством работы агента.** Они проверяют контракт и защиту от неверных источников, но не показывают, что модель найдёт передачу `5.4.4 → 5.3.3` в реальных документах.
3. **Frontend полностью отсутствует.** Без трёх экранов жюри не увидит основной сценарий, панель источников, человеческую проверку и отчёт.
4. **Не подтверждён запуск PostgreSQL/API.** До начала UI нужно выполнить миграции, запустить `/api/health`, загрузить настоящие файлы и сохранить их после перезапуска.
5. **Нужен контрольный набор для всех must-have.** Реальная пара хорошо показывает передачу и изменение модальности, но не даёт явно подписанный истинный пример потери и дублирования. Нужны отдельные небольшие синтетические пары, явно помеченные как тестовые.

### P1 — важно, но не должно задержать основной путь

1. **PDF/XLSX.** Парсеры существуют, но каждый заявленный формат нужно проверить настоящим небольшим файлом. Не обещать OCR сканов: сейчас он не входит в основу.
2. **Авторизация.** Есть `User` и development seed, но нет регистрации, входа, JWT, владения анализами и серверной проверки прав. Это не нарушение требований MVP; не тратить на это время до работающего demo.
3. **История и повторный запуск.** API-поддержка есть, но её нужно показать в UI только после основного анализа.
4. **Переводы.** Интерфейс, пояснения и отчёт могут быть RU/KK/EN; оригинальные цитаты и заметки нельзя переводить или изменять.
5. **Асинхронная очередь.** Один worker и PostgreSQL advisory lock достаточно для хакатона. Не добавлять Redis/Celery, пока не пройдён основной путь.

## 4. Рекомендуемый стек: не менять без причины

| Слой | Рекомендация | Почему |
|---|---|---|
| Frontend | React + TypeScript + Vite | Быстро для таблиц, вкладок, фильтров и трёх языков |
| API-клиент | HeyAPI из `backend/openapi.json` | Типы и операции не расходятся с FastAPI |
| Данные клиента | TanStack Query или лёгкие feature-hooks | Опрос статуса запуска, кэширование и повторные запросы без тяжёлого глобального store |
| Backend | Текущий FastAPI modular monolith | Уже подготовлен и соответствует объёму MVP |
| База | PostgreSQL + async SQLAlchemy + Alembic | Это фактический выбор текущего кода; SQLite не поддерживается из-за JSONB и миграций |
| Файлы | Текущая постоянная директория backend | Документ и исходные блоки должны переживать перезапуск |
| AI | OpenAI Responses API через текущий ограниченный агент | Структурированный результат, инструменты, строгая валидация evidence ID |
| Экспорт | Текущий HTML + CSV | HTML можно печатать в PDF; не усложнять PDF-генерацию сейчас |

**Не добавлять сейчас:** отдельную vector DB, микросервисы, несколько автономных агентов, чат, графовую БД, полную RBAC-авторизацию, OCR и внешние HR-интеграции.

## 5. Лучший frontend: три страницы, не больше

### 5.1. История — `/`

Показывает анализы: название, дата, документы, статус, количество вопросов. Главная кнопка — **«Новое сравнение»**. Пустое состояние должно предлагать открыть демо-пару.

### 5.2. Новое сравнение — `/new`

Две одинаковые зоны: **«До реорганизации»** и **«После реорганизации»**. В каждой — список файлов, формат, номер редакции, число распознанных блоков и предупреждения. Кнопка **«Анализировать»** доступна только когда обе стороны содержат читаемые документы.

### 5.3. Результаты — `/analyses/:id`

Один рабочий экран с тремя вкладками:

| Вкладка | Что показывает |
|---|---|
| Структура | Подразделение «До» → подразделение «После» → статус → источник |
| Функции и риски | Обязанность, старый/новый исполнитель, тип изменения, вопрос, review-статус |
| Заключение | Что изменилось, что нужно проверить, ограничения, экспорт |

Справа открывается **EvidencePanel** с двумя колонками: исходный пункт «До» и исходный пункт «После». Здесь пользователь подтверждает, уточняет или отклоняет вывод и пишет заметку.

### 5.4. UI-компоненты первой очереди

```text
pages/
  HistoryPage
  NewAnalysisPage
  AnalysisPage
components/
  UploadSide
  AnalysisStatus
  StructureTable
  FindingsTable
  EvidencePanel
  ReviewControls
  ReportView
  LanguageSwitcher
```

Не нужен отдельный маркетинговый экран, граф-«паутинка» или страница настроек. На ноутбуке список занимает около 55% ширины, доказательства — 45%. На телефоне панель доказательств открывается поверх списка на весь экран.

## 6. Правила UI, которые дают доверие

1. Цвет не является единственным признаком статуса. Нужны текст и иконка.
2. **«Передана» — это изменение, а не ошибка.** Не окрашивать передачу красным.
3. Разделять `change_type` и `issue_type`:
   - изменение: сохранена, переформулирована, передана, разделена, новая, соответствие не найдено;
   - вопрос: потенциальный пробел, пересечение, конфликт, изменение обязательности, неясность.
4. «Соответствие не найдено» означает только отсутствие в предоставленном комплекте и проведённый поиск; это не доказательство отмены работы компании.
5. Любой важный вывод без кнопки/ссылки «Открыть доказательства» — дефект блокирующего уровня.
6. Переключение RU/ҚАЗ/EN не должно повторно запускать анализ. Меняются UI, сохранённые объяснения и отчёт; оригинал пункта остаётся оригиналом.
7. Состояние `partial` всегда видно пользователю вместе с причиной, а не маскируется как «готово».

## 8. Killer features, которые стоят времени

### 1. Карта передачи функций

Показывать связь `старая обязанность → новый исполнитель/несколько исполнителей → источники`. Это главная разница с Word Compare и обычным AI-поиском.

### 2. Evidence-first вывод

Сначала два пункта, затем объяснение. Не показывать «уверенность модели» как вероятность истины. Лучше использовать простой статус: `подтверждено источниками`, `нужна проверка`, `недостаточно данных`.

### 3. Проверка изменения обязательности

Отдельно находить замену «осуществляется / должен» на «может». Реальный пример в п. 9.15 делает эту функцию сильной и проверяемой.

### 4. Контроль полноты поиска

Для возможной потери показывать: сколько функций и документов «После» было проверено, какие кандидаты рассмотрены и почему вывод ограничен. Это превращает «AI так сказал» в проверяемый процесс.

### 5. Human-in-the-loop итог

Отчёт отделяет подтверждённые аналитиком замечания от открытых вопросов. Такой подход соответствует тому, что AI даёт рекомендацию, а не юридическое решение.

## 10. Честный Definition of Done

Delphi можно называть готовым к защите, только если выполняются все условия:

- [ ] Жюри может самостоятельно запустить проект по README.
- [ ] Реальная пара «До/После» загружается и сохраняется.
- [ ] Агент действительно запускается и не подменяется заранее написанным JSON.
- [ ] Показаны структура, перенос функции, потенциальная потеря, дублирование/конфликт, доказательства и заключение.
- [ ] Все существенные findings открывают настоящие пункты нужной редакции.
- [ ] Реальная и синтетическая демонстрации явно различаются.
- [ ] Отчёт совпадает с тем, что показано на экране.
- [ ] Ограничения — сканы, отсутствующие приложения, неполный вход, языки, отсутствие прав доступа — видны пользователю и описаны в README.

**Самая правильная защита:** не обещать «AI полностью проверил реорганизацию». Сказать: **«Delphi быстро показывает проверяемые изменения и вопросы, а ответственный сотрудник принимает решение, видя источники».**
