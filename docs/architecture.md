# Delphi — архитектура и контракты

## 1. Выбранный стек и архитектура

**Один модульный Python-сервис, PostgreSQL и один агент с инструментами. Frontend — следующий этап.**

| Часть | Решение | Причина |
|---|---|---|
| Frontend | React + TypeScript + Vite; обычные CSS-переменные и простые компоненты | Достаточно для трёх страниц, таблиц и панели источников; [Vite](https://vite.dev/guide/) |
| Переводы UI | i18next / react-i18next; словари ru, kk, en | Централизованные подписи и смена языка; [i18next](https://www.i18next.com/overview/getting-started) |
| Backend | FastAPI + Pydantic; тонкие маршруты и отдельные сервисы | Типизированный API, бизнес-правила и обработка документов в одном приложении |
| Файлы | python-docx, pypdf, openpyxl, MD-адаптер | Единый результат из нескольких форматов |
| AI | OpenAI SDK, Responses API, структурированный результат и вызовы инструментов | Модель ищет соответствия через функции приложения; [Function calling](https://developers.openai.com/api/docs/guides/function-calling), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) |
| Данные | PostgreSQL + async SQLAlchemy/asyncpg + Alembic; постоянная директория файлов | UUID, JSONB, внешние ключи, транзакции и версионируемая схема; SQLite не поддерживается |
| Задачи | Один выполняющийся анализ; асинхронная задача в одном процессе; опрос статуса UI | Простая конфигурация на хакатон |
| Экспорт | Серверный HTML и CSV | Результат собирается из сохранённых данных и версии проверки человеком |
| Контракт frontend | Pydantic response DTO + стабильные OpenAPI operation_id | JSON-схема экспортируется без запуска сервера и служит входом для HeyAPI |
| Запуск | Один backend worker; PostgreSQL в Docker; постоянные данные БД и файлов | Блокировка PostgreSQL допускает только один исполнитель приложения; команды — в backend/README.md |

Модель задаётся через OPENAI_MODEL. Проверка небольшим реальным запросом относится к следующему этапу запуска; сейчас такие запросы не выполняются. Доступность, качество на контрольной паре и время ответа ещё нужно подтвердить. Ключ хранится только на сервере; отсутствие настройки возвращает явную ошибку, а не подставной AI-результат.

Structured Outputs проверяет форму ответа, а не истинность вывода. Нужны проверки источников, смысла и контрольные примеры.

Простой исполнитель и очередь в одном процессе — ограничение прототипа. Состояния хранятся в PostgreSQL; после перезапуска незавершённые запуски помечаются interrupted, повтор создаёт новое сравнение. Приложение удерживает advisory lock PostgreSQL, чтобы второй worker не забирал работу и не помечал чужие запуски прерванными. Это не распределённая очередь: для нескольких исполнителей понадобится отдельный механизм задач.

Направление зависимостей: **api → services → models / parsers / agent**. Маршруты принимают запрос и возвращают DTO; сервисы управляют транзакциями, доступом к текущему сравнению и состояниями запуска. DomainError преобразуется в HTTP-ошибку централизованно. ORM-модели не служат схемами внешнего API. Пакеты агента разделяют извлечение, сопоставление, проверку структуры и поиск возможной потерянной функции.

~~~mermaid
flowchart TD
    UI["UI: история / загрузка / результаты"] --> API["FastAPI"]
    API --> Services["Сервисы: правила и транзакции"]
    Services --> DB[("PostgreSQL и файлы")]
    Services --> Parse["Чтение блоков и реестр источников"]
    Parse --> Extract["Подразделения, роли и функции"]
    Extract --> Match["Точные совпадения и кандидаты"]
    Match --> Agent["Один агент: сопоставить и проверить"]
    Agent --> Tools["Поиск пунктов / чтение источников / функции подразделения"]
    Tools --> Agent
    Agent --> Validate["Проверка ID, цитат, полноты и спорных выводов"]
    Validate --> DB
    DB --> UI
    UI --> Review["Проверка человеком"]
    Review --> DB
    DB --> Report["Заключение, переводы, экспорт"]
~~~

Не вводим отдельные сервисы, векторную базу или координацию нескольких агентов до того, как обычный путь проходит проверки.

## 2. Backend: последовательность анализа

### Шаг 1. Прочитать и сохранить документы

Сохраняем исходный файл, его хеш, сторону сравнения, название, формат и блоки текста. Повтор одинакового содержимого на одной стороне возвращает ошибку duplicate_document; одинаковые документы на разных сторонах допустимы. Совпадение имён файлов ничего не доказывает.

До разбора проверяем лимит размера, расширение и фактическую структуру файла. Заявленный MIME-тип не считается доказательством формата. Для DOCX/XLSX проверяем нужные части ZIP-контейнера и лимиты распаковки; повреждённый или неподдерживаемый файл получает понятную ошибку. Численные лимиты задаём конфигурацией и указываем возле загрузки.

Файл хранится под сгенерированным именем вне каталога раздачи frontend. Исходное имя сохраняется как метаданные. Читать источник можно через API соответствующего анализа.

Для каждого блока: ID документа, путь к блоку, исходный текст, раздел/пункт при достоверном извлечении. Для поиска отдельно готовим нормализованный текст.

Адаптеры:

- **DOCX:** абзацы и таблицы в исходном порядке. Номера, набранные текстом, сохраняем; автоматическую нумерацию читаем отдельно либо честно используем ссылку на блок без выдуманного номера. [Document objects](https://python-docx.readthedocs.io/en/latest/api/document.html).
- **PDF:** текст и настоящая страница PDF. Пустой/нечитаемый текст — предупреждение. pypdf не выполняет OCR. [Extract Text](https://pypdf.readthedocs.io/en/stable/user/extract-text.html).
- **XLSX:** лист, ячейки/диапазон, заголовки и контекст строки. Минимальный проверяемый сценарий — таблица «Подразделение / Функция / Подчинённость»; необычные схемы требуют разбора и не объявляются универсально поддержанными. [openpyxl](https://openpyxl.readthedocs.io/en/stable/tutorial.html).
- **MD:** исходные строки и номера пунктов; без выдуманных номеров страниц.

Специальные проверки этих образцов: пункты 3.9–3.11 склеены даже в DOCX; заголовки 10–14 находятся внутри обычных абзацев, а стили заголовков используются в оглавлении; приложение 1 отсутствует; пустой 5.5.3 нельзя дополнять. Парсер только по строкам или стилям заголовков недостаточен.

Метаданные Word дают en-US/ar-SA для фактически русского текста и недостоверное число страниц. Язык определяем по содержимому; ссылку строим по пункту, абзацу и позиции фрагмента. Надёжных номеров страниц у этого DOCX нет.

Если делим длинный блок, фрагмент хранит смещение в сохранённом исходном тексте и родительский контекст. Показываем измеряемое покрытие: например, обработано N из M извлечённых блоков. Это не процент понимания документа.

### Шаг 2. Получить подразделения и функции

Модель извлекает структурированные записи из блоков с уже известными ID. Для функции нужны:

**кто выполняет → действие → объект → область/условия → обязательность → источник.**

Должность, подразделение и группа подразделений различаются. Если раздел адресован нескольким директорам, сохраняем общий контекст и специализацию: нельзя назначать каждому весь функционал без учёта области.

Обрабатывать блоки по разделам с родительскими заголовками. Первый проход покрывает оба комплекта; не ограничиваться только главой 5, потому что обязанности встречаются и в главе 9. Непрочитанные/необработанные блоки отмечаются отдельно.

### Шаг 3. Сопоставить

Код ищет точные нормализованные совпадения и похожие кандидаты; сравнивает также исполнителя, условия и обязательность. Совпавший текст с другим исполнителем может означать передачу.

Агент решает неоднозначные пары. Разрешены связи 1→1, 1→несколько, несколько→1; один номер пункта не равен одной функции.

Для небольшого текущего набора используем полный структурированный перечень функций и поиск по пунктам. Отдельная векторная база не нужна. Лексический поиск сам по себе не доказывает отсутствие соответствия, особенно между языками.

### Шаг 4. Проверить возможные проблемы

Перед статусом «соответствие не найдено»:

1. Проверить функции всех подразделений комплекта «После», а не только прежнего исполнителя.
2. Найти синонимы, общие и более узкие формулировки, новые номера.
3. Прочитать найденные пункты вместе с родительскими заголовками.
4. Зафиксировать рассмотренные кандидаты и пробелы покрытия.
5. При неполном поиске вернуть «недостаточно данных / не завершена проверка».

Даже при полном поиске вывод звучит: **«Соответствие не найдено в предоставленном комплекте»**, а не «компания прекратила выполнять обязанность».

Для пересечений сравниваем функции внутри «После»: действие, объект, область, роль. Одинаковый глагол не означает дублирование. Иерархическая ответственность, совместная работа и разные территории могут объяснять похожие пункты.

Потенциальный конфликт — например, один исполнитель проверяет собственное исполнение по сопоставимому объекту. Нужны два источника и объяснение; без внешнего нормативного источника не объявляем это нарушением закона.

### Шаг 5. Проверить результат и сохранить

Программа проверяет, что ID существуют, принадлежат этому запуску и нужной стороне, а цитаты получены из сохранённого исходника. Неизвестный или чужой ID — технически невалидный результат: его возвращаем на исправление либо исключаем из findings и заключения, показывая ошибку обработки. Статус «вопрос для проверки» подходит для неоднозначного смысла **существующего** источника. Отдельно проверяются логика связи, роль исполнителя и условия.

Модель не пишет «точную цитату» по памяти: выбирает существующие ID и фрагменты; приложение извлекает исходный текст. Если выбирается часть блока, проверяем границы и точное совпадение.

Готовые и частичные результаты сохраняются вместе с версией обработки. Заключение собирается из тех же findings, что показаны в UI, без отдельного свободного пересказа с новыми фактами.

## 3. Один агент и его инструменты

| Инструмент | Что делает | Когда нужен |
|---|---|---|
| search_clauses(side, query, filters) | Ищет в документах текущего запуска; возвращает ID и фрагменты | Проверить перенос в другую часть комплекта |
| get_clause(source_id) | Возвращает исходный пункт и родительский контекст | Подтвердить найденное совпадение |
| get_unit_functions(side, unit_id) | Возвращает извлечённые обязанности подразделения с источниками | Сравнить распределение функций |
| check_references(document_id) | Находит цели внутренних ссылок | Дополнительная проверка после основных функций |

Извлечение и финальная проверка — этапы одной системы, а не отдельные «персоны», которые спорят между собой. Проверка человеком остаётся последним этапом.

Ограничения исполнения задаются настройками request_timeout_seconds, run_timeout_seconds, max_batch_chars и max_tool_rounds. Запросы внутри одного анализа выполняются последовательно; число раундов инструментов ограничено. Отказ провайдера, неверная схема или исчерпанный лимит не заменяются ответом другого провайдера либо заранее подготовленным результатом. Значения лимитов и скорость ещё нужно проверить на реальной паре.

Если лимит исчерпан, сохраняем выполненную часть и список непроверенных функций. Статус «готово» нельзя выставлять просто потому, что цикл закончился.

Для демонстрации агентности сохраняем короткий журнал операций: поиск, найденные source_id, прочитанные пункты, результат проверки. Скрытые рассуждения модели не нужны. Текст документа — анализируемые данные, а не команды для агента.

## 4. Минимальная модель данных и API

Используем только PostgreSQL через SQLAlchemy 2 и asyncpg. Таблицы создаются миграциями Alembic; приложение не создаёт их автоматически при старте. Основные ID имеют тип UUID, время хранится с часовым поясом, структурированные результаты — в JSONB. Настройки подключения обязательны; альтернативной базы по умолчанию нет.

| Сущность | Основные поля |
|---|---|
| Analysis | id, title, created_at |
| Document | id, analysis_id, side, filename, storage_key, hash, revision_label, format, detected_language, parse_status, warnings |
| SourceBlock | id, document_id, locator, clause_no (необязательно), parent_id, original_text, normalized_text |
| Run | id, analysis_id, immutable_document_ids, state, stage, coverage, structure, model, output_language, pipeline_version, review_revision (изначально 0), started_at, finished_at, errors, trace; один Run на Analysis в MVP |
| Unit | id, run_id, side, kind (подразделение / роль / группа), name_original, parent_unit_id (необязательно), source_ids |
| Function | id, run_id, side, owner_unit_ids, actor_original, action, object, scope, condition, modality, source_ids |
| Finding | id, run_id, title, change_type, issue_type (включая scope_changed/modality_changed), before_function_ids, after_function_ids, explanation, recommendation, search (результат проверки комплекта «После») |
| FindingEvidence | id, finding_id, source_id, evidence_role (before / after / context), start_offset (необязательно), end_offset (необязательно) |
| Review | finding_id, status, note, updated_at |
| Translation / Export | run_id, review_revision, locale, payload, created_at |
| User | Подготовка тестовых пользователей для seed; модель не подключена к авторизации и владению анализами |

Источник уникален по документу и позиции, а не только по номеру пункта. Запуск фиксирует свои документы: последующая загрузка не должна незаметно изменить старое заключение.

Каждая связь many-to-many сохраняет несколько ID с обеих сторон. Отсутствующая сторона — допустимый пустой список для нового/потенциально отсутствующего функционала.

FindingEvidence — основной список доказательств вывода. Поле source_ids в ответе API для Finding вычисляется из этих связей, а не хранится как независимая копия. Текст excerpt сервер получает из SourceBlock.original_text по проверенным смещениям; модель не записывает его свободным текстом. Для переноса нужны источники обеих сторон, для пересечения — два источника «После», для предполагаемой потери — старый источник и описание выполненного поиска.

PostgreSQL проверяет внешние ключи, уникальность запуска анализа, позицию блока в документе и допустимые состояния. ID внутри JSONB-массивов дополнительно проверяет приложение: принадлежность запуску, стороне и существующим функциям/источникам.

Review содержит последнее решение человека. Его сохранение и увеличение Run.review_revision выполняются в одной транзакции; новый отчёт и перевод используют текущую ревизию. Это предотвращает показ старого заключения после изменения проверки. Полный журнал действий пользователей в MVP не создаём.

Снимок отчёта и перевод привязаны к run_id + review_revision + locale; для экспорта добавляется format. Перед запросом перевода сервис сохраняет снимок и освобождает транзакцию. Перед записью результата повторно блокирует Run и проверяет ревизию; изменение проверки во время запроса возвращает 409. HTML показывает подтверждённые, непроверенные и отклонённые выводы отдельно, сохраняя оригинальные цитаты. CSV переводит заголовки, а значения функций оставляет исходными. Отчёты доступны только для completed/partial.

| Запрос | Назначение |
|---|---|
| POST /api/analyses | Создать черновик |
| GET /api/analyses | История |
| POST /api/analyses/:id/documents | Загрузить файлы с полем side |
| PATCH /api/analyses/:id/documents/:document_id | Исправить side или revision_label только до запуска |
| DELETE /api/analyses/:id/documents/:document_id | Убрать файл из черновика; не менять уже выполненный запуск |
| GET /api/analyses/:id/documents/:document_id/sources | Проверить извлечённые блоки до запуска |
| POST /api/analyses/:id/runs | Запустить анализ; вернуть run_id сразу |
| POST /api/analyses/:id/repeat | Создать новое сравнение с копией выбранных документов; вернуть новый analysis_id |
| GET /api/analyses/:id | Документы и единственный запуск |
| GET /api/runs/:run_id | Стадия, покрытие, подразделения, число выводов, ошибки |
| GET /api/runs/:run_id/functions | Функции с владельцами и ссылками на источники |
| GET /api/runs/:run_id/findings | Выводы с типами изменений и статусами проверки |
| GET /api/findings/:finding_id/evidence | Связи FindingEvidence и точные фрагменты исходников |
| GET /api/sources/:source_id | Исходный текст, положение и ID родительского блока |
| PUT /api/findings/:finding_id/review | Сохранить статус и заметку; одинаковые значения не повышают ревизию |
| POST /api/runs/:run_id/translations | Подготовить пояснения на выбранном языке |
| GET /api/runs/:run_id/report?lang=ru&format=html | Отчёт по сохранённой версии проверки |
| GET /api/runs/:run_id/functions.csv?lang=ru | Таблица функций |
| GET /api/health | Готовность процесса и наличие настройки AI |

Запрос запуска передаёт output_language и явный allow_partial. Пробелы чтения требуют согласия на частичный результат; это не разрешение объявить непроверенные обязанности отсутствующими. Один Run на Analysis закреплён ограничением БД, состав документов после запуска неизменяем. Повтор создаёт новый Analysis. Состояния: queued, running, completed, partial, failed, interrupted; frontend впоследствии опрашивает их примерно раз в две секунды.

Прогресс сохраняется между этапами. Все извлечённые объекты и выводы записываются одной транзакцией после возврата агента; промежуточные объекты при тайм-ауте не восстанавливаются. Документ без читаемых блоков блокирует запуск даже при allow_partial=true.

Типизированные схемы запросов/ответов находятся в backend/app/schemas, operation_id заданы в маршрутах явно. Скрипт backend/scripts/export_openapi.py готовит контракт без запуска сервера, подключения к БД и вызова модели. Он предназначен для последующей генерации клиента HeyAPI; frontend и клиент пока не созданы.

У общего демо одна рабочая область. Модель User и seed-данные — подготовка для разработки, а не вход в приложение или проверка прав. Изоляция разных организаций и полноценное управление доступом остаются следующим этапом.

### Решение по предложению авторизации и другой схемы БД

| Предложение | Решение для пяти часов |
|---|---|
| FastAPI + SQLite или PostgreSQL | FastAPI + PostgreSQL по уточнённому выбору команды; один вариант конфигурации |
| User, регистрация, вход, JWT, admin/analyst | User и seed подготовлены; регистрация, вход, JWT и применение ролей не реализованы |
| Analysis.before_document_id / after_document_id | Не используем: сохраняем несколько Document на сторону через analysis_id + side |
| FindingEvidence | Включаем: явная связь вывода с источником, ролью и положением фрагмента |
| Clause и единственный source_clause_id | SourceBlock поддерживает нумерованные и ненумерованные блоки; функция может иметь несколько источников |
| Unit.parent_name и одна роль владельца функции | Используем стабильные ID; сохраняем различие ролей, групп и подразделений |
| ReviewNote с user_id | Пока Review без фиктивного пользователя; user_id появится вместе с проверяемой авторизацией |
| Проверка существования AI-ссылок | Дополнительно проверяем запуск, сторону, контекст и обоснованность вывода |

Хеширование паролей и JWT — возможная техническая основа будущего входа; FastAPI показывает такой вариант в [официальном руководстве](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/). Они не заменяют проверку прав на конкретные записи. Для многопользовательского этапа владелец определяется сервером; права проверяются на каждом запросе к анализу, файлу, источнику, заметке и отчёту. Правило «admin видит всё» остаётся предложением для отдельного решения, а не принятой политикой. [OWASP: проверка прав доступа](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

Структура подготовленного backend:

~~~text
backend/
  app/
    main.py, config.py, db.py       приложение, настройки и соединение
    api/                          тонкие маршруты и зависимости
    schemas/                      типизированные запросы/ответы для OpenAPI
    services/                     analyses, documents, runs, workflow, results,
                                  findings, reports, translations
    domain/                       общие ошибки бизнес-правил
    reporting/                    форматирование отчётов, CSV и подписи RU/KK/EN
    models/                       таблицы и связи SQLAlchemy
    parsers/                      DOCX, PDF, XLSX, Markdown
    agent/                        engine, model_client, extraction, matching,
                                  structure, missing, validation, tools, prompts
  migrations/                     версии схемы Alembic
  scripts/                        seed.py, export_openapi.py
  fixtures/                       описание демо и тестовых пользователей
  tests/                          проверки парсеров и агента
~~~

Frontend, его страницы и компоненты остаются планом в [product.md](product.md). Команды настройки и границы проверки backend — в [backend/README.md](../backend/README.md). Подготовленный код ещё не означает готовность полного пользовательского сценария.

Параметр finding в URL — состояние выбранной строки UI; backend проверяет принадлежность этого ID текущему запуску. Выбор языка хранится отдельно от вычисленного результата. Подробные взаимодействия описаны в [product.md](product.md).
